# Step 3. 관계 및 카디널리티 설계

## 1. 관계 설계 원칙

관계 설계는 기존 결정 사항을 따른다.

| 원칙 | 내용 |
| --- | --- |
| 비식별 관계 | 부모 엔티티의 식별자가 자식 엔티티의 기본 식별자에 포함되지 않는다. |
| 독립 식별자 | 모든 엔티티는 독립적인 `id`를 가진다. |
| Zero or Many | 부모 입장에서 자식 데이터는 0개 이상 존재할 수 있다. |
| MVP 제외 준수 | Detection, EventStatusHistory 등 제외 범위 도메인은 관계로 만들지 않는다. |

## 2. 관계 목록

| 관계 ID | 부모 엔티티 | 자식 엔티티 | 관계 | 설명 |
| --- | --- | --- | --- | --- |
| R-01 | User | Event | 1 : 0..N | 한 명의 관제사는 0개 이상의 이벤트를 담당하거나 확인할 수 있다. |
| R-02 | Equipment | Event | 1 : 0..N | 하나의 장비는 0개 이상의 이벤트를 탐지할 수 있다. |
| R-03 | User | Comment | 1 : 0..N | 한 명의 관제사는 0개 이상의 코멘트를 작성할 수 있다. |
| R-04 | Event | Comment | 1 : 0..N | 하나의 이벤트는 0개 이상의 코멘트를 가질 수 있다. |

## 3. 관계별 상세

### R-01. User - Event

| 항목 | 내용 |
| --- | --- |
| 관계 | User 1 : 0..N Event |
| 의미 | 관제사가 이벤트를 확인하거나 담당할 수 있다. |
| 선택성 | Event의 User 참조는 선택이다. |
| 이유 | AI가 최초 이벤트를 등록할 때 아직 관제사가 배정되지 않을 수 있다. |
| 관계 유형 | 비식별 관계 |

### R-02. Equipment - Event

| 항목 | 내용 |
| --- | --- |
| 관계 | Equipment 1 : 0..N Event |
| 의미 | 하나의 장비가 여러 탐지 이벤트를 만들 수 있다. |
| 선택성 | Event의 Equipment 참조는 필수다. |
| 이유 | 이벤트는 어떤 장비가 탐지했는지 식별되어야 한다. |
| 관계 유형 | 비식별 관계 |

### R-03. User - Comment

| 항목 | 내용 |
| --- | --- |
| 관계 | User 1 : 0..N Comment |
| 의미 | 관제사가 여러 처리 기록을 작성할 수 있다. |
| 선택성 | Comment의 User 참조는 필수다. |
| 이유 | 처리 기록은 누가 작성했는지 추적되어야 한다. |
| 관계 유형 | 비식별 관계 |

### R-04. Event - Comment

| 항목 | 내용 |
| --- | --- |
| 관계 | Event 1 : 0..N Comment |
| 의미 | 하나의 이벤트에 여러 처리 기록 또는 메모가 달릴 수 있다. |
| 선택성 | Comment의 Event 참조는 필수다. |
| 이유 | 코멘트는 반드시 특정 이벤트에 대한 기록이어야 한다. |
| 관계 유형 | 비식별 관계 |

## 4. 관계로 만들지 않는 연결

| 연결 후보 | 제외 이유 |
| --- | --- |
| Event - Detection | 다중 객체 탐지는 MVP 제외다. |
| Event - EventStatusHistory | 별도 상태 변경 이력은 MVP 제외다. |
| Equipment - Location | Equipment 자체 좌표 관리는 MVP 제외다. |
| User - RolePermission | 복잡한 권한 관리는 MVP 제외다. |

## 5. Step 3 결론

최종 관계는 네 개로 제한한다.

```text
User 1 --- 0..N Event
Equipment 1 --- 0..N Event
User 1 --- 0..N Comment
Event 1 --- 0..N Comment
```

모든 관계는 비식별 관계이며, 부모 엔티티 입장에서 자식은 0개 이상 존재할 수 있다.
