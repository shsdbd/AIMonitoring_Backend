# Step 9. 우선순위 및 MVP 매핑

## 1. 우선순위 분류 기준

요구사항 우선순위는 MoSCoW 방식으로 분류한다.

| 분류 | 의미 |
| --- | --- |
| Must-have | MVP에서 반드시 포함해야 하는 핵심 요구사항 |
| Should-have | 가능하면 포함하되, 일정이 부족하면 축소 가능한 요구사항 |
| Could-have | 있으면 좋지만 MVP 성공 여부를 좌우하지 않는 요구사항 |
| Won't-have | 이번 MVP에서는 제외할 요구사항 |

이번 MVP의 핵심은 **AI 탐지 이벤트가 백엔드를 거쳐 관제사 화면에서 확인되고, 관제사가 상태를 관리할 수 있는 흐름**이다.

## 2. Must-have 요구사항

| ID | 요구사항 | 이유 |
| --- | --- | --- |
| FR-01 | AI 모듈이 전달한 장애물 탐지 결과를 수신할 수 있어야 한다. | AI 기반 관제 흐름의 시작점이다. |
| FR-02 | 탐지 결과를 신규 장애물 이벤트로 등록할 수 있어야 한다. | 관제사가 확인할 수 있는 이벤트 단위가 필요하다. |
| FR-03 | 이벤트에 장애물 종류, 신뢰도, 위치, 발생 시각 정보를 포함해야 한다. | 관제 판단의 최소 정보다. |
| FR-04 | 프론트엔드가 장애물 강조 박스를 표시할 수 있는 좌표 정보를 제공해야 한다. | 교수님이 강조한 관제 확인 장면에 필요하다. |
| FR-05 | 이벤트의 우선순위 정보를 제공할 수 있어야 한다. | 관제사가 먼저 볼 이벤트를 판단하는 데 필요하다. |
| FR-06 | 관제사가 신규 이벤트를 인지할 수 있도록 이벤트 정보를 제공해야 한다. | 발견 지연 문제를 줄이는 핵심 요구다. |
| FR-07 | 관제사가 등록된 이벤트 목록을 확인할 수 있어야 한다. | 관제 화면의 기본 흐름이다. |
| FR-08 | 관제사가 특정 이벤트의 상세 정보를 확인할 수 있어야 한다. | 실제 장애물 여부 판단에 필요하다. |
| FR-09 | 관제사가 이벤트 상태를 변경할 수 있어야 한다. | 처리 흐름 관리에 필수다. |
| FR-10 | 상태 변경 결과를 저장하고 최신 상태를 제공해야 한다. | 관제 업무의 일관성을 유지한다. |
| FR-13 | 오탐 이벤트를 실제 처리 대상과 구분할 수 있어야 한다. | AI 탐지 시스템에서 오탐 처리는 필수 흐름이다. |
| FR-15 | 탐지 근거 이미지 또는 영상 참조 정보를 제공할 수 있어야 한다. | 관제사가 실제 장애물 여부를 판단해야 한다. |
| DR-03 | AI가 탐지한 장애물 이벤트 정보를 관리해야 한다. | 핵심 도메인 데이터다. |
| DR-04 | 이벤트에는 관제 판단에 필요한 기본 정보가 포함되어야 한다. | 목록/상세 확인에 필요하다. |
| DR-05 | 이벤트에는 bbox 정보가 포함되어야 한다. | 장애물 강조 표시를 위한 데이터다. |
| DR-08 | 이벤트 상태를 관리해야 한다. | 처리 흐름에 필요하다. |

## 3. Should-have 요구사항

| ID | 요구사항 | 이유 |
| --- | --- | --- |
| FR-11 | 관제사가 처리 기록 또는 확인 메모를 남길 수 있어야 한다. | 처리 이력 관리에 중요하지만, MVP 시연에서는 상태 변경만으로 축소 가능하다. |
| FR-12 | 이벤트별 처리 기록을 조회할 수 있어야 한다. | 기록 작성 기능과 함께 구현되면 업무 완성도가 높아진다. |
| DR-01 | 관제사를 식별할 수 있는 사용자 정보를 관리해야 한다. | 처리자 추적에 필요하지만, MVP에서는 단일 관제사 가정으로 축소 가능하다. |
| DR-02 | 탐지 장비를 식별할 수 있는 장비 정보를 관리해야 한다. | 어떤 장비가 탐지했는지 중요하지만, MVP에서는 장비 ID만으로 시작 가능하다. |
| DR-07 | 이벤트별 처리 기록 또는 확인 메모를 관리해야 한다. | 조치 이력 관리에 필요하다. |
| AR-01 | 관제사만 이벤트 목록과 상세 정보를 확인할 수 있어야 한다. | 실제 서비스에서는 필요하지만, MVP 시연에서는 단순화 가능하다. |
| AR-02 | 관제사만 이벤트 상태를 변경할 수 있어야 한다. | 실제 서비스 보안 요구이지만 구현 범위에 따라 단계화 가능하다. |
| AR-03 | 관제사만 코멘트를 작성할 수 있어야 한다. | 코멘트 기능 구현 여부에 종속된다. |

## 4. Could-have 요구사항

| ID | 요구사항 | 이유 |
| --- | --- | --- |
| AR-05 | 관리자 역할이 장비와 사용자 정보를 관리할 수 있어야 한다. | 운영 완성도는 높지만 MVP 핵심 흐름은 아니다. |
| NFR-11 | 주요 요청과 오류를 추적할 수 있어야 한다. | 개발/운영에 유용하지만 MVP 기능 시연의 핵심은 아니다. |
| NFR-12 | 장애물 종류와 장비 종류 확장성을 가져야 한다. | 향후 확장성 요구다. |
| NFR-14 | User, Equipment, Event, Comment 책임이 구분되어야 한다. | 구조적으로 중요하지만 실제 구현 우선순위는 MVP 범위에 따라 조정된다. |

## 5. Won't-have 요구사항

| ID | 제외 항목 | 제외 이유 |
| --- | --- | --- |
| WH-01 | AI 모델 학습 및 추론 로직 구현 | AI 파트의 책임이며 백엔드 MVP 범위가 아니다. |
| WH-02 | 프론트엔드 화면 디자인 세부 구현 | 프론트엔드 파트의 책임이다. |
| WH-03 | 대규모 분산 처리 인프라 | 졸업 작품 MVP에는 과도하다. |
| WH-04 | 완전한 고가용성 구성 | 단일 백엔드/DB 흐름 검증이 우선이다. |
| WH-05 | 다중 객체 탐지를 위한 별도 Detection 도메인 | 현재 범위는 이벤트당 단일 장애물 탐지로 둔다. |
| WH-06 | EventStatusHistory 별도 이력 테이블 | MVP에서는 이벤트 상태와 코멘트로 처리 흐름을 표현한다. |
| WH-07 | Equipment 자체 지도 좌표 관리 | MVP에서는 Event 위치 정보로 지도 표시를 처리한다. |

## 6. MVP 핵심 흐름

MVP에서 반드시 보여줘야 할 흐름은 다음과 같다.

```text
AI 탐지 결과 발생
-> 백엔드가 이벤트로 등록
-> 프론트엔드가 신규 이벤트를 표시
-> 관제사가 이벤트 목록/상세 확인
-> 관제사가 위치, 신뢰도, 탐지 근거, bbox 강조 영역 확인
-> 관제사가 상태를 확인 중/처리 완료/오탐 등으로 변경
-> 변경 결과가 저장되고 다시 조회됨
```

## 7. MVP에서 협의가 필요한 항목

다음 항목은 MVP에 필요하지만 세부 방식이 아직 미정이므로 AI/프론트엔드 파트와 협의가 필요하다.

| 항목 | 이유 |
| --- | --- |
| AI -> 백엔드 공식 요청 형식 | 백엔드 수신 요구사항 구현에 직접 영향 |
| bbox 좌표 기준 | 프론트 강조 박스 표시 정확도에 영향 |
| priority 값 체계 | 관제사가 우선순위를 해석하는 방식에 영향 |
| 신규 이벤트 알림 방식 | 관제사의 신규 이벤트 인지 방식에 영향 |
| 이미지/영상 참조 방식 | 관제사의 탐지 근거 확인 방식에 영향 |

## 8. Step 9 결론

MVP의 우선순위는 **AI 탐지 이벤트 수신, 이벤트 등록, 관제사 확인, 상태 변경**에 집중한다.

처리 기록, 관제사 인증, 장비/사용자 관리, 운영 로그는 중요하지만 일정과 구현 난이도에 따라 Should-have 또는 Could-have로 둔다.

이번 MVP에서는 대규모 인프라, AI 모델 자체 구현, 프론트엔드 세부 디자인, 다중 객체 탐지, 별도 상태 이력 테이블은 제외한다.
