# Step 6. 비기능 요구사항 정의

## 1. 비기능 요구사항 정의 기준

비기능 요구사항은 시스템이 기능을 수행할 때 충족해야 하는 품질 조건을 정의한다.

이 프로젝트의 백엔드 핵심 가치는 **AI 모델과 프론트엔드 사이의 안정적인 데이터 전달**이며, 그 다음으로 **빠른 데이터 처리**를 중요하게 본다. 따라서 비기능 요구사항은 안정성, 성능, 데이터 정합성, 보안, 운영 가능성 중심으로 정리한다.

## 2. 비기능 요구사항 목록

| ID | 분류 | 비기능 요구사항 | 설명 |
| --- | --- | --- | --- |
| NFR-01 | 안정성 | 시스템은 AI 모듈이 전달한 탐지 이벤트를 누락 없이 저장하는 것을 우선해야 한다. | 백엔드의 1순위 가치는 안정적인 데이터 전달이다. |
| NFR-02 | 안정성 | 이벤트 저장 후 프론트엔드가 동일한 이벤트를 조회할 수 있어야 한다. | AI -> 백엔드 -> 프론트 흐름의 연속성이 필요하다. |
| NFR-03 | 성능 | 시스템은 신규 탐지 이벤트를 관제사가 지연 없이 확인할 수 있는 수준으로 처리해야 한다. | 구체 시간 기준은 추후 성능 목표에서 확정한다. |
| NFR-04 | 성능 | 이벤트 목록 조회는 관제사가 업무 중 반복적으로 사용해도 불편하지 않은 응답성을 가져야 한다. | 관제 화면의 기본 사용성에 직접 영향을 준다. |
| NFR-05 | 데이터 정합성 | 장애물 이벤트에는 관제 판단에 필요한 필수 정보가 누락되지 않아야 한다. | 위치, 장애물 종류, 신뢰도, 상태, 탐지 근거 등이 필요하다. |
| NFR-06 | 데이터 정합성 | 이벤트 상태는 정의된 업무 상태 범위 안에서만 관리되어야 한다. | 미확인, 확인 중, 처리 완료, 오탐 등 상태 혼선을 줄인다. |
| NFR-07 | 데이터 정합성 | 좌표, 신뢰도, 우선순위, bbox 정보는 잘못된 값이 저장되지 않도록 검증되어야 한다. | 관제 판단과 지도/화면 표시 오류를 방지한다. |
| NFR-08 | 보안 | 관제사 기능은 허가된 사용자만 접근할 수 있어야 한다. | 구체 인증 방식은 아직 미정이다. |
| NFR-09 | 보안 | AI 모듈이 탐지 이벤트를 전송할 때 무단 요청을 방지할 수 있어야 한다. | 구체 인증 방식은 AI 파트와 협의가 필요하다. |
| NFR-10 | 가용성 | 시스템은 관제 업무 중 지속적으로 접근 가능해야 한다. | 단, MVP 수준의 고가용성 인프라까지 요구하지는 않는다. |
| NFR-11 | 운영성 | 장애 발생 시 원인을 파악할 수 있도록 주요 요청과 오류를 추적할 수 있어야 한다. | 이벤트 수신 실패나 저장 실패 원인 파악이 필요하다. |
| NFR-12 | 확장성 | 향후 장애물 종류, 장비 종류, 관제 기록이 늘어나도 기존 흐름을 크게 깨지 않고 확장 가능해야 한다. | 졸업 작품 이후 기능 확장을 고려한다. |
| NFR-13 | 호환성 | 프론트엔드가 지도, 목록, 상세, 강조 박스를 표현할 수 있도록 일관된 데이터 구조를 제공해야 한다. | 프론트 연동 안정성에 필요하다. |
| NFR-14 | 유지보수성 | 도메인별 책임이 분리되어 향후 User, Equipment, Event, Comment 확장이 가능해야 한다. | 현재 Event 중심 프로토타입에서 4개 도메인 구조로 확장해야 한다. |

## 3. 안정성 요구사항

| ID | 요구사항 | 이유 |
| --- | --- | --- |
| NFR-01 | AI 탐지 이벤트는 수신 후 가능한 한 누락 없이 저장되어야 한다. | 탐지 이벤트 누락은 관제 실패로 이어질 수 있다. |
| NFR-02 | 저장된 이벤트는 프론트엔드 조회 결과와 일관되어야 한다. | 관제사가 보는 화면이 실제 저장 상태와 다르면 처리 혼선이 생긴다. |
| NFR-15 | 이벤트 상태 변경은 저장 성공 여부가 명확해야 한다. | 관제사가 처리했다고 생각했지만 저장되지 않는 상황을 방지해야 한다. |

## 4. 성능 요구사항

| ID | 요구사항 | 이유 |
| --- | --- | --- |
| NFR-03 | 신규 이벤트 수신과 조회 가능 상태 전환은 관제 업무에 지장을 주지 않을 정도로 빨라야 한다. | 발견 지연 문제를 줄이는 것이 서비스 목표다. |
| NFR-04 | 이벤트 목록과 상세 정보 조회는 관제사가 반복 조회해도 지연을 크게 느끼지 않아야 한다. | 관제 업무는 목록 확인과 상세 확인을 반복한다. |
| NFR-16 | MVP 단계에서는 과도한 대용량 트래픽보다는 단일 관제 흐름의 안정성을 우선한다. | 현재 프로젝트 범위와 개발 기간을 고려한다. |

## 5. 보안 및 권한 요구사항

| ID | 요구사항 | 이유 |
| --- | --- | --- |
| NFR-08 | 관제사 기능은 허가된 사용자만 사용할 수 있어야 한다. | 임의 사용자가 상태를 변경하거나 기록을 조작하면 안 된다. |
| NFR-09 | AI 이벤트 등록 요청은 신뢰 가능한 AI 모듈에서 온 요청인지 확인할 수 있어야 한다. | 무단 이벤트 생성과 잘못된 관제 알림을 방지한다. |
| NFR-17 | 보안 방식은 MVP 범위와 팀 구현 가능성을 고려해 결정해야 한다. | JWT, API Key, IP 제한 등 방식은 아직 확정되지 않았다. |

## 6. 데이터 품질 요구사항

| ID | 요구사항 | 이유 |
| --- | --- | --- |
| NFR-05 | 이벤트에는 관제 판단에 필요한 최소 정보가 있어야 한다. | 정보가 부족하면 관제사가 실제 장애물 여부를 판단하기 어렵다. |
| NFR-06 | 이벤트 상태값은 정의된 업무 상태 안에서만 변경되어야 한다. | 상태값 혼선을 줄이고 목록 필터링과 처리 흐름을 단순화한다. |
| NFR-07 | 위치, 신뢰도, bbox, 우선순위 값은 유효 범위를 벗어나지 않아야 한다. | 지도 표시, 강조 박스 표시, 우선순위 판단의 오류를 줄인다. |

## 7. 운영 및 유지보수 요구사항

| ID | 요구사항 | 이유 |
| --- | --- | --- |
| NFR-11 | 이벤트 수신, 저장, 조회, 상태 변경 과정에서 오류 원인을 추적할 수 있어야 한다. | 개발 및 시연 중 문제 원인 파악이 중요하다. |
| NFR-12 | 장애물 종류와 장비 종류가 늘어나도 요구사항 구조가 확장 가능해야 한다. | 현재는 동물 사체 중심이지만 향후 낙하물 등으로 확장할 수 있다. |
| NFR-14 | User, Equipment, Event, Comment의 책임이 구분되어야 한다. | 이후 도메인 모델링과 구현 확장 시 충돌을 줄인다. |

## 8. 비기능 요구사항에서 제외하는 항목

| 제외 항목 | 제외 이유 |
| --- | --- |
| 대규모 분산 처리 인프라 | MVP와 졸업 작품 범위에서는 과도하다. |
| 클라우드 오브젝트 스토리지 필수 도입 | 현재는 정적 이미지 저장으로도 MVP 검증이 가능하다. |
| 완전한 고가용성 구성 | 단일 FastAPI/DB 컨테이너 기반 검증이 우선이다. |
| 상세 인증 구현 방식 확정 | 요구사항 단계에서는 보안 필요성만 정의하고 방식은 추후 결정한다. |

## 9. Step 6 결론

비기능 요구사항의 핵심은 다음과 같다.

1. AI 탐지 이벤트가 누락 없이 저장되고 프론트엔드로 전달되어야 한다.
2. 관제사가 신규 이벤트를 지연 없이 확인할 수 있어야 한다.
3. 위치, 신뢰도, bbox, 상태 등 관제 판단 데이터의 정합성이 보장되어야 한다.
4. 관제사 기능과 AI 이벤트 등록에는 적절한 접근 통제가 필요하다.
5. MVP에서는 대규모 인프라보다 안정적인 단일 관제 흐름을 우선한다.
