# Step 1. 입력 문서 검토 요약

## 1. 현재 단계 인식

현재 단계는 `requirements-decomposition`입니다.

목표는 앞 단계에서 승인된 서비스 목표와 문제 정의를 바탕으로, **도로 관제사가 실제로 어떤 흐름으로 시스템을 사용하는지**를 요구사항 수준으로 분해하는 것입니다.

특히 이번 단계의 핵심은 교수님이 강조하신 **관제사 시나리오**를 명확히 만드는 것입니다.

## 2. 입력 문서에서 확인한 핵심 맥락

| 구분 | 확인 내용 |
| --- | --- |
| 프로젝트명 | AI 기반 실시간 도로 장애물 관제 시스템 |
| 핵심 탐지 대상 | 도로 위 동물 사체 |
| 1차 사용자 | 도로 관제사 |
| 핵심 문제 | 사람이 직접 순찰하거나 CCTV 영상을 감시해야 해서 장애물 발견이 늦어짐 |
| 백엔드 핵심 가치 | AI 모델과 프론트엔드 사이의 안정적인 데이터 전달, 빠른 데이터 처리 |
| 완성 장면 | AI가 장애물을 감지하면 백엔드 처리를 거쳐 프론트 화면에 알림이 뜨고, 관제사가 영상과 강조 표시를 확인함 |

## 3. 현재 확정된 요구사항 근거

| 항목 | 현재 상태 |
| --- | --- |
| AI 탐지 이벤트 | AI 모듈이 장애물 탐지 결과를 백엔드로 전달하는 흐름이 필요 |
| 관제사 확인 | 관제사는 프론트 화면에서 장애물 발생 알림을 확인해야 함 |
| 위치 정보 | 이벤트에는 위도/경도 정보가 포함되어야 함 |
| 시각 확인 | 관제사는 이미지/영상 화면에서 장애물 강조 표시를 확인해야 함 |
| 강조 박스 | AI가 bbox 좌표를 제공하고, 프론트엔드가 해당 좌표로 박스를 그리는 방향 |
| 이벤트 우선순위 | Event에는 `priority` 개념을 포함하는 방향 |
| 처리 상태 | 이벤트 상태 변경 및 처리 흐름이 필요 |

## 4. 현재 미결정 사항

| 미결정 사항 | 요구사항 단계에서의 처리 방식 |
| --- | --- |
| AI -> 백엔드 공식 요청 형식 | 상세 API 형식으로 확정하지 않고, “AI 탐지 결과를 수신해야 한다”는 요구사항으로만 다룸 |
| bbox 좌표 기준 | 픽셀/정규화 여부는 미정으로 두고, “프론트가 강조 표시 가능한 좌표 정보가 필요하다”로 표현 |
| 실시간 알림 방식 | SSE/WebSocket/Polling 중 구현 방식은 정하지 않고, “관제사가 신규 이벤트를 인지할 수 있어야 한다”로 표현 |
| 영상 연계 방식 | 백엔드 관리 여부는 미정으로 두고, “관제사가 탐지 근거 화면을 확인할 수 있어야 한다”로 표현 |
| 인증 방식 | 구체 방식은 정하지 않고, “관제사 역할 기반 접근이 필요할 수 있다” 수준으로 둠 |

## 5. 요구사항 분해 방향

이번 요구사항 단계에서는 기술 구현보다 **관제사의 실제 업무 흐름**을 중심으로 정리합니다.

핵심 시나리오는 다음 흐름으로 잡겠습니다.

```text
AI가 동물 사체 탐지
-> 백엔드가 탐지 이벤트 수신
-> 프론트 관제 화면에 신규 알림 표시
-> 관제사가 이벤트 확인
-> 지도 위치와 탐지 근거 화면 확인
-> 장애물 강조 박스 확인
-> 관제사가 상태를 변경하거나 처리 기록을 남김
-> 처리 완료 또는 오탐으로 종료
```

## 6. Step 1 결론

입력 문서 기준으로, 이 프로젝트의 요구사항은 단순한 이벤트 저장 API가 아니라 **관제사가 늦은 발견 문제를 줄이기 위해 AI 탐지 이벤트를 빠르게 인지하고 확인·처리하는 업무 흐름**을 중심으로 분해해야 합니다.
