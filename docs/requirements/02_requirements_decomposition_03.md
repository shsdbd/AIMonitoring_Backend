# Step 3. 사용자 시나리오 작성

## 1. 시나리오 작성 관점

이 단계의 핵심은 기능 목록이 아니라, **도로 관제사가 실제 관제 업무 중 AI 탐지 이벤트를 어떻게 인지하고 확인하며 처리하는지**를 구체적인 흐름으로 정리하는 것이다.

시나리오는 다음 두 관점을 함께 고려한다.

| 관점 | 역할 |
| --- | --- |
| 도로 관제사 | 신규 장애물 알림을 확인하고, 위치와 탐지 근거를 바탕으로 상황을 판단하며, 처리 상태를 관리한다. |
| 시스템 | AI 탐지 결과를 수신하고, 관제사가 확인 가능한 이벤트로 제공하며, 처리 상태와 기록을 유지한다. |

## 2. 대표 Happy Path: AI 탐지 이벤트 확인 및 처리

### 시나리오 H-1. 동물 사체 탐지 이벤트가 정상적으로 관제사에게 전달되는 경우

| 단계 | Actor | 행동 |
| --- | --- | --- |
| 1 | AI 모듈 | 도로 위 동물 사체로 의심되는 객체를 탐지한다. |
| 2 | AI 모듈 | 탐지 결과를 백엔드로 전달한다. 탐지 결과에는 장애물 종류, 신뢰도, 위치 정보, 장애물 강조 표시를 위한 좌표 정보, 탐지 근거 이미지 또는 영상 참조 정보가 포함될 수 있다. |
| 3 | 시스템 | AI 탐지 결과를 신규 장애물 이벤트로 등록한다. |
| 4 | 시스템 | 프론트엔드 관제 화면에서 신규 이벤트를 인지할 수 있도록 제공한다. |
| 5 | 도로 관제사 | 관제 화면에서 신규 장애물 알림 또는 신규 이벤트 목록을 확인한다. |
| 6 | 도로 관제사 | 이벤트의 장애물 종류, 탐지 신뢰도, 발생 시각, 우선순위, 위치 정보를 확인한다. |
| 7 | 도로 관제사 | 지도 또는 위치 표시를 통해 장애물이 발생한 지점을 확인한다. |
| 8 | 도로 관제사 | 탐지 근거 화면에서 장애물 강조 박스를 확인한다. |
| 9 | 도로 관제사 | 탐지 결과가 실제 동물 사체로 판단되면 이벤트 상태를 확인 중 또는 처리 대상으로 변경한다. |
| 10 | 도로 관제사 | 필요한 경우 조치 내용 또는 확인 메모를 기록한다. |
| 11 | 도로 관제사 | 현장 조치가 끝났거나 상황이 종료되면 이벤트 상태를 처리 완료로 변경한다. |
| 12 | 시스템 | 변경된 이벤트 상태와 기록을 저장하고, 이후 조회 시 최신 상태를 제공한다. |

## 3. 보조 Happy Path: 관제사가 이벤트 목록을 점검하는 경우

### 시나리오 H-2. 관제사가 누적 이벤트를 확인하고 우선순위가 높은 이벤트부터 확인하는 경우

| 단계 | Actor | 행동 |
| --- | --- | --- |
| 1 | 도로 관제사 | 관제 화면에서 현재 등록된 장애물 이벤트 목록을 확인한다. |
| 2 | 시스템 | 최신 이벤트와 미처리 이벤트를 관제사가 식별할 수 있도록 제공한다. |
| 3 | 도로 관제사 | 우선순위, 발생 시각, 처리 상태를 기준으로 먼저 확인할 이벤트를 선택한다. |
| 4 | 도로 관제사 | 선택한 이벤트의 상세 정보를 확인한다. |
| 5 | 도로 관제사 | 위치와 탐지 근거 화면을 확인하고 후속 조치 여부를 판단한다. |
| 6 | 도로 관제사 | 판단 결과에 따라 이벤트 상태를 변경하거나 코멘트를 남긴다. |

## 4. Exception Path: 오탐으로 판단되는 경우

### 시나리오 E-1. AI가 탐지했지만 관제사가 실제 장애물이 아니라고 판단하는 경우

| 단계 | Actor | 행동 |
| --- | --- | --- |
| 1 | AI 모듈 | 동물 사체로 의심되는 객체를 탐지해 이벤트를 발생시킨다. |
| 2 | 시스템 | 신규 이벤트를 등록하고 관제 화면에서 확인 가능하게 제공한다. |
| 3 | 도로 관제사 | 이벤트 상세 화면에서 위치, 신뢰도, 탐지 근거 화면, 장애물 강조 박스를 확인한다. |
| 4 | 도로 관제사 | 실제 장애물이 아니거나 판단 근거가 부족하다고 판단한다. |
| 5 | 도로 관제사 | 이벤트 상태를 오탐으로 변경한다. |
| 6 | 도로 관제사 | 필요한 경우 오탐 판단 사유를 코멘트로 기록한다. |
| 7 | 시스템 | 오탐 상태와 코멘트를 저장하고, 이후 목록에서 해당 이벤트가 실제 처리 대상과 구분되도록 제공한다. |

## 5. Exception Path: 관제사가 즉시 판단하기 어려운 경우

### 시나리오 E-2. 탐지 근거가 불명확해 추가 확인이 필요한 경우

| 단계 | Actor | 행동 |
| --- | --- | --- |
| 1 | 도로 관제사 | 신규 이벤트를 확인한다. |
| 2 | 도로 관제사 | 위치 정보와 탐지 근거 화면을 확인했지만 실제 장애물 여부를 즉시 확정하지 못한다. |
| 3 | 도로 관제사 | 이벤트 상태를 확인 중으로 변경한다. |
| 4 | 도로 관제사 | 추가 확인이 필요한 이유를 코멘트로 기록한다. |
| 5 | 시스템 | 해당 이벤트가 아직 종결되지 않은 상태임을 유지한다. |
| 6 | 도로 관제사 | 추가 확인 후 처리 완료 또는 오탐으로 최종 상태를 변경한다. |

## 6. Exception Path: AI 탐지 결과에 필수 정보가 부족한 경우

### 시나리오 E-3. 위치 또는 탐지 근거가 부족해 관제 판단이 어려운 경우

| 단계 | Actor | 행동 |
| --- | --- | --- |
| 1 | AI 모듈 | 장애물 탐지 결과를 백엔드로 전달한다. |
| 2 | 시스템 | 탐지 결과에 관제 판단에 필요한 필수 정보가 부족한지 확인한다. |
| 3 | 시스템 | 필수 정보가 부족한 경우 해당 이벤트를 정상 관제 대상으로 처리하지 않거나, 관제사가 정보 부족 상태를 인지할 수 있도록 제공한다. |
| 4 | 도로 관제사 | 정보 부족 이벤트를 확인한 경우, 실제 조치 대상으로 판단하지 않고 추가 확인 또는 제외 처리한다. |

> 이 시나리오는 상세 검증 방식이나 오류 응답 형식을 정의하지 않는다. 구체적인 인터페이스 규격은 이후 연계 요구사항 및 구현 단계에서 다룬다.

## 7. 시나리오에서 도출되는 핵심 요구 흐름

| 흐름 | 설명 |
| --- | --- |
| 탐지 | AI 모듈이 도로 위 동물 사체를 탐지한다. |
| 수신 | 백엔드가 탐지 결과를 수신한다. |
| 등록 | 시스템이 탐지 결과를 관제 이벤트로 등록한다. |
| 인지 | 관제사가 신규 이벤트를 알림 또는 목록을 통해 인지한다. |
| 확인 | 관제사가 위치, 신뢰도, 우선순위, 탐지 근거 화면을 확인한다. |
| 판단 | 관제사가 실제 장애물인지 오탐인지 판단한다. |
| 처리 | 관제사가 상태를 변경하고 필요한 기록을 남긴다. |
| 종결 | 이벤트가 처리 완료 또는 오탐 상태로 종료된다. |

## 8. 협의가 필요한 시나리오 요소

다음 사항은 요구사항 단계에서 흐름은 정의하되, 세부 방식은 AI/프론트엔드 파트와 협의가 필요하다.

| 항목 | 협의 필요 이유 |
| --- | --- |
| AI 탐지 결과 형식 | 백엔드가 어떤 데이터를 필수로 받을지 정해야 함 |
| bbox 좌표 기준 | 프론트엔드가 정확한 위치에 강조 박스를 그리려면 기준 좌표계가 필요함 |
| 실시간 알림 방식 | 관제사가 신규 이벤트를 인지하는 방식은 프론트엔드 구현과 연결됨 |
| 영상/이미지 표시 방식 | 백엔드가 영상 참조를 관리할지, 프론트엔드가 직접 연결할지 결정 필요 |
| priority 값 체계 | 관제사가 이벤트 우선순위를 해석할 수 있는 기준이 필요함 |

## 9. Step 3 결론

관제사 시나리오의 핵심은 **AI가 탐지한 이벤트가 관제사의 확인, 판단, 처리, 종결 흐름으로 자연스럽게 이어지는 것**이다.

따라서 이후 요구사항은 다음 질문을 기준으로 분해한다.

1. 관제사는 신규 장애물 이벤트를 어떻게 인지하는가?
2. 관제사는 어떤 정보를 보고 실제 장애물 여부를 판단하는가?
3. 관제사는 판단 결과를 시스템에 어떻게 남기는가?
4. 시스템은 이 흐름을 누락 없이 저장하고 다시 조회할 수 있는가?
