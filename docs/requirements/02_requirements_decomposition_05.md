# Step 5. 기능 요구사항 정의

## 1. 기능 요구사항 정의 기준

이 단계에서는 Step 4의 유스케이스를 바탕으로, 시스템이 반드시 수행해야 하는 동작을 기능 요구사항으로 정리한다.

기능 요구사항은 **무엇을 제공해야 하는가**에 집중하며, 구체적인 API 경로, DB 컬럼 설계, 내부 구현 방식은 이후 설계 단계에서 다룬다.

## 2. 기능 요구사항 목록

| ID | 기능 요구사항 | 관련 유스케이스 | 우선 설명 |
| --- | --- | --- | --- |
| FR-01 | 시스템은 AI 모듈이 전달한 장애물 탐지 결과를 수신할 수 있어야 한다. | UC-01 | AI 탐지 결과가 관제 이벤트 흐름의 시작점이다. |
| FR-02 | 시스템은 수신한 탐지 결과를 신규 장애물 이벤트로 등록할 수 있어야 한다. | UC-01 | 관제사가 확인할 수 있는 이벤트 단위로 관리해야 한다. |
| FR-03 | 시스템은 이벤트에 장애물 종류, 탐지 신뢰도, 발생 위치, 발생 시각 정보를 포함해야 한다. | UC-01, UC-04 | 관제 판단에 필요한 기본 정보다. |
| FR-04 | 시스템은 프론트엔드가 장애물 강조 박스를 표시할 수 있는 좌표 정보를 제공할 수 있어야 한다. | UC-05 | 관제사가 AI가 판단한 장애물 위치를 시각적으로 확인해야 한다. |
| FR-05 | 시스템은 이벤트의 우선순위 정보를 제공할 수 있어야 한다. | UC-03, UC-04 | 관제사가 먼저 확인할 이벤트를 판단하는 데 필요하다. |
| FR-06 | 시스템은 관제사가 신규 이벤트를 인지할 수 있도록 이벤트 정보를 제공해야 한다. | UC-02 | 알림 방식은 미정이지만 신규 이벤트 인지는 필수다. |
| FR-07 | 시스템은 관제사가 등록된 이벤트 목록을 확인할 수 있도록 해야 한다. | UC-03 | 누적 이벤트와 미처리 이벤트 확인이 필요하다. |
| FR-08 | 시스템은 관제사가 특정 이벤트의 상세 정보를 확인할 수 있도록 해야 한다. | UC-04 | 위치, 신뢰도, 상태, 탐지 근거 확인이 필요하다. |
| FR-09 | 시스템은 관제사가 이벤트 상태를 변경할 수 있도록 해야 한다. | UC-06, UC-08 | 확인 중, 처리 완료, 오탐 등 업무 상태 관리가 필요하다. |
| FR-10 | 시스템은 이벤트 상태 변경 결과를 저장하고 이후 조회 시 최신 상태를 제공해야 한다. | UC-06 | 처리 흐름의 일관성을 유지해야 한다. |
| FR-11 | 시스템은 관제사가 이벤트에 대한 처리 기록 또는 확인 메모를 남길 수 있도록 해야 한다. | UC-07 | 조치 이력과 판단 근거 관리가 필요하다. |
| FR-12 | 시스템은 이벤트별 처리 기록을 조회할 수 있도록 해야 한다. | UC-07 | 같은 이벤트에 대한 후속 확인이 가능해야 한다. |
| FR-13 | 시스템은 오탐으로 판단된 이벤트를 실제 처리 대상 이벤트와 구분할 수 있어야 한다. | UC-08 | 관제사가 불필요한 후속 조치를 줄일 수 있어야 한다. |
| FR-14 | 시스템은 필수 탐지 정보가 부족한 이벤트를 정상 이벤트와 구분하거나 등록을 제한할 수 있어야 한다. | E-3 | 관제 판단이 불가능한 데이터가 정상 처리되는 것을 방지해야 한다. |
| FR-15 | 시스템은 탐지 근거 이미지 또는 영상 참조 정보를 관제사가 확인 가능한 형태로 제공할 수 있어야 한다. | UC-04, UC-05 | 관제사가 실제 장애물 여부를 판단하려면 시각 근거가 필요하다. |

| ID | 관제사 행동 | 시스템이 제공해야 하는 기능 |
| --- | --- | --- |
| FR-16 | 관제사는 신규 이벤트를 확인한다. | 시스템은 신규 이벤트 여부를 식별 가능한 형태로 제공해야 한다. |
| FR-17 | 관제사는 이벤트 위치를 확인한다. | 시스템은 이벤트의 위치 정보를 제공해야 한다. |
| FR-18 | 관제사는 탐지 근거 화면을 확인한다. | 시스템은 이미지 또는 영상 참조 정보를 제공해야 한다. |
| FR-19 | 관제사는 장애물 강조 영역을 확인한다. | 시스템은 프론트엔드가 강조 박스를 그릴 수 있는 좌표 정보를 제공해야 한다. |
| FR-20 | 관제사는 실제 장애물 여부를 판단한다. | 시스템은 장애물 종류, 신뢰도, 위치, 우선순위, 탐지 근거 정보를 함께 제공해야 한다. |
| FR-21 | 관제사는 처리 상태를 변경한다. | 시스템은 상태 변경 요청을 반영하고 저장해야 한다. |
| FR-22 | 관제사는 조치 내용이나 오탐 사유를 기록한다. | 시스템은 이벤트별 기록을 저장하고 조회 가능하게 해야 한다. |

## 5. 기능 요구사항에서 제외하는 항목

| 제외 항목 | 제외 이유 |
| --- | --- |
| AI 모델 학습 및 추론 로직 | AI 파트의 책임이며 백엔드 요구사항 범위가 아니다. |
| 프론트엔드 화면 디자인 세부사항 | 요구사항 단계에서는 화면이 제공해야 할 정보와 행동만 정의한다. |
| 실시간 알림 구현 방식 | SSE, WebSocket, Polling 중 무엇을 사용할지는 아직 미정이다. |
| AI -> 백엔드 상세 요청 포맷 | 이후 연계 요구사항 및 구현 지시서 단계에서 확정한다. |
| DB 테이블/컬럼 상세 설계 | 이후 도메인 모델링과 데이터베이스 설계 단계에서 확정한다. |

## 6. Step 5 결론

기능 요구사항의 핵심은 다음 5가지로 압축된다.

1. AI 탐지 결과를 이벤트로 등록한다.
2. 관제사가 신규 이벤트를 인지하고 목록/상세 정보를 확인한다.
3. 관제사가 위치와 탐지 근거, 강조 박스를 보고 실제 장애물 여부를 판단한다.
4. 관제사가 이벤트 상태와 처리 기록을 남긴다.
5. 시스템은 이 모든 정보를 저장하고 프론트엔드가 다시 조회할 수 있게 제공한다.
