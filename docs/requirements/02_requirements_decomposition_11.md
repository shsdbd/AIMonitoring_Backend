# Step 11. 최종 요구사항 명세서

## 1. 문서 목적

이 문서는 `requirements-decomposition` 단계의 최종 산출물이다.

앞선 `service-goal-definition` 단계에서 확정한 서비스 목표와 문제 정의를 바탕으로, AI 기반 실시간 도로 장애물 관제 시스템의 사용자 시나리오, 유스케이스, 기능/비기능 요구사항, 데이터/권한/연계 요구사항, 수용 기준, MVP 우선순위를 종합한다.

핵심은 교수님이 강조한 **도로 관제사 시나리오**를 중심으로 요구사항을 개발 가능한 수준까지 분해하는 것이다.

## 2. 프로젝트 요약

| 항목 | 내용 |
| --- | --- |
| 프로젝트명 | AI 기반 실시간 도로 장애물 관제 시스템 |
| 핵심 탐지 대상 | 도로 위 동물 사체 |
| 1차 사용자 | 도로 관제사 |
| 핵심 문제 | 사람이 직접 순찰하거나 CCTV 영상을 감시해야 해서 장애물 발견이 늦어진다. |
| 백엔드 핵심 가치 | AI 모델과 프론트엔드 사이의 안정적인 데이터 전달, 빠른 데이터 처리 |
| 목표 장면 | AI가 장애물을 감지하면 백엔드 처리를 거쳐 프론트 화면에 알림이 뜨고, 관제사가 위치, 탐지 근거 화면, 장애물 강조 표시를 확인한다. |

## 3. 대표 관제사 시나리오

```text
AI가 도로 위 동물 사체를 탐지한다.
-> AI 모듈이 탐지 결과를 백엔드에 전달한다.
-> 백엔드는 탐지 결과를 신규 장애물 이벤트로 등록한다.
-> 프론트엔드 관제 화면은 신규 이벤트를 관제사가 인지할 수 있게 표시한다.
-> 관제사는 이벤트 목록 또는 알림을 통해 신규 이벤트를 확인한다.
-> 관제사는 이벤트 상세에서 위치, 장애물 종류, 신뢰도, 우선순위, 발생 시각을 확인한다.
-> 관제사는 탐지 근거 화면과 장애물 강조 박스를 보고 실제 장애물 여부를 판단한다.
-> 실제 장애물로 판단되면 상태를 확인 중 또는 처리 완료로 변경한다.
-> 오탐으로 판단되면 상태를 오탐으로 변경한다.
-> 필요한 경우 관제사는 처리 기록 또는 판단 사유를 남긴다.
-> 시스템은 변경된 상태와 기록을 저장하고 이후 조회 시 최신 정보를 제공한다.
```

## 4. 주요 Actor

| Actor | 역할 |
| --- | --- |
| 도로 관제사 | 신규 장애물 이벤트를 확인하고, 실제 장애물 여부를 판단하며, 상태와 기록을 관리한다. |
| AI 모듈 | 도로 위 장애물을 탐지하고 탐지 결과를 백엔드에 전달한다. |
| 프론트엔드 관제 화면 | 관제사가 이벤트를 인지하고 확인할 수 있도록 목록, 상세, 위치, 강조 표시를 제공한다. |
| 백엔드 시스템 | AI 탐지 결과를 수신, 저장, 제공하고 이벤트 상태와 처리 기록을 관리한다. |

## 7. 비기능 요구사항

| ID | 분류 | 비기능 요구사항 |
| --- | --- | --- |
| NFR-01 | 안정성 | 시스템은 AI 모듈이 전달한 탐지 이벤트를 누락 없이 저장하는 것을 우선해야 한다. |
| NFR-02 | 안정성 | 이벤트 저장 후 프론트엔드가 동일한 이벤트를 조회할 수 있어야 한다. |
| NFR-03 | 성능 | 시스템은 신규 탐지 이벤트를 관제사가 지연 없이 확인할 수 있는 수준으로 처리해야 한다. |
| NFR-04 | 성능 | 이벤트 목록 조회는 관제사가 업무 중 반복적으로 사용해도 불편하지 않은 응답성을 가져야 한다. |
| NFR-05 | 데이터 정합성 | 장애물 이벤트에는 관제 판단에 필요한 필수 정보가 누락되지 않아야 한다. |
| NFR-06 | 데이터 정합성 | 이벤트 상태는 정의된 업무 상태 범위 안에서만 관리되어야 한다. |
| NFR-07 | 데이터 정합성 | 좌표, 신뢰도, 우선순위, bbox 정보는 잘못된 값이 저장되지 않도록 검증되어야 한다. |
| NFR-08 | 보안 | 관제사 기능은 허가된 사용자만 접근할 수 있어야 한다. |
| NFR-09 | 보안 | AI 모듈이 탐지 이벤트를 전송할 때 무단 요청을 방지할 수 있어야 한다. |
| NFR-10 | 가용성 | 시스템은 관제 업무 중 지속적으로 접근 가능해야 한다. |
| NFR-11 | 운영성 | 장애 발생 시 원인을 파악할 수 있도록 주요 요청과 오류를 추적할 수 있어야 한다. |
| NFR-12 | 확장성 | 향후 장애물 종류, 장비 종류, 관제 기록이 늘어나도 기존 흐름을 크게 깨지 않고 확장 가능해야 한다. |

## 12. MVP 범위

### Must-have

- AI 탐지 결과 수신
- 신규 장애물 이벤트 등록
- 이벤트 목록 조회
- 이벤트 상세 확인
- 위치 정보 제공
- 탐지 근거 이미지 또는 영상 참조 제공
- bbox 기반 장애물 강조 표시 데이터 제공
- priority 제공

## 15. 최종 결론

이번 요구사항 분해 단계의 결론은 다음과 같다.

1. 이 시스템의 핵심 요구사항은 **AI 탐지 이벤트를 도로 관제사의 확인, 판단, 처리 흐름으로 연결하는 것**이다.
2. MVP는 AI 탐지 이벤트 수신, 이벤트 등록, 관제사 목록/상세 확인, bbox 기반 강조 표시, 상태 변경, 오탐 구분을 반드시 포함해야 한다.
3. 처리 기록, 인증, 사용자/장비 관리 기능은 중요하지만 일정과 구현 범위에 따라 Should-have로 조정할 수 있다.
4. AI와 프론트엔드의 데이터 연계 방식은 아직 확정되지 않았으므로, 후속 단계에서 반드시 각 파트와 협의해야 한다.
5. 다음 단계에서는 이 요구사항을 바탕으로 MVP 범위 확정 및 도메인 모델링으로 넘어갈 수 있다.
