# Step 4. 유스케이스 정의

## 1. 유스케이스 정의 기준

이 단계에서는 Step 3의 관제사 시나리오를 바탕으로, Actor와 System 사이의 상호작용을 유스케이스 단위로 정의한다.

구현 방식, API 상세, DB 설계는 다루지 않고 **사용자가 시스템을 통해 달성해야 하는 업무 목표**를 중심으로 정리한다.

## 2. Actor 정의

| Actor | 설명 |
| --- | --- |
| 도로 관제사 | 관제 화면에서 신규 장애물 이벤트를 확인하고, 위치와 탐지 근거를 바탕으로 상태를 관리하는 1차 사용자 |
| AI 모듈 | 도로 위 동물 사체를 탐지하고 탐지 결과를 시스템에 전달하는 외부 시스템 |
| 프론트엔드 관제 화면 | 관제사가 이벤트를 인지하고 확인할 수 있도록 정보를 표시하는 사용자 접점 |
| 백엔드 시스템 | AI 탐지 결과를 수신, 저장, 제공하고 이벤트 상태와 기록을 관리하는 시스템 |

## 3. 유스케이스 목록

| ID | 유스케이스명 | 주 Actor | 목적 |
| --- | --- | --- | --- |
| UC-01 | AI 탐지 이벤트 등록 | AI 모듈 | AI가 탐지한 동물 사체 이벤트를 시스템에 등록한다. |
| UC-02 | 신규 이벤트 인지 | 도로 관제사 | 관제사가 새로 발생한 장애물 이벤트를 인지한다. |
| UC-03 | 이벤트 목록 확인 | 도로 관제사 | 관제사가 현재 등록된 이벤트와 처리 상태를 확인한다. |
| UC-04 | 이벤트 상세 확인 | 도로 관제사 | 관제사가 특정 이벤트의 위치, 신뢰도, 우선순위, 탐지 근거를 확인한다. |
| UC-05 | 장애물 강조 영역 확인 | 도로 관제사 | 관제사가 AI가 탐지한 장애물 위치를 화면상 강조 박스로 확인한다. |
| UC-06 | 이벤트 상태 변경 | 도로 관제사 | 관제사가 이벤트를 확인 중, 처리 완료, 오탐 등으로 분류한다. |
| UC-07 | 처리 기록 작성 | 도로 관제사 | 관제사가 확인 결과나 조치 내용을 기록한다. |
| UC-08 | 오탐 이벤트 구분 | 도로 관제사 | 실제 장애물이 아닌 이벤트를 오탐으로 분류해 실제 처리 대상과 구분한다. |

## 4. 유스케이스 상세

### UC-01. AI 탐지 이벤트 등록

| 항목 | 내용 |
| --- | --- |
| 주 Actor | AI 모듈 |
| 목표 | AI가 탐지한 동물 사체 이벤트를 관제사가 확인 가능한 시스템 이벤트로 등록한다. |
| 사전 조건 | AI 모듈이 도로 위 장애물을 탐지한다. |
| 기본 흐름 | AI 모듈이 탐지 결과를 백엔드 시스템에 전달한다. 시스템은 탐지 결과를 신규 이벤트로 등록한다. |
| 대안 흐름 | 필수 정보가 부족하면 시스템은 정상 관제 이벤트로 처리하지 않거나 정보 부족 상태를 식별할 수 있어야 한다. |
| 사후 조건 | 신규 이벤트가 관제 화면에서 확인 가능한 상태가 된다. |

### UC-02. 신규 이벤트 인지

| 항목 | 내용 |
| --- | --- |
| 주 Actor | 도로 관제사 |
| 목표 | 관제사가 신규 장애물 이벤트 발생 사실을 빠르게 인지한다. |
| 사전 조건 | 시스템에 신규 이벤트가 등록되어 있다. |
| 기본 흐름 | 시스템은 관제 화면에서 신규 이벤트를 식별 가능하게 제공한다. 관제사는 알림 또는 목록 변화를 통해 신규 이벤트를 확인한다. |
| 대안 흐름 | 실시간 알림 방식이 확정되지 않은 경우에도 관제사는 목록 갱신을 통해 신규 이벤트를 인지할 수 있어야 한다. |
| 사후 조건 | 관제사가 확인할 이벤트를 선택할 수 있다. |

### UC-03. 이벤트 목록 확인

| 항목 | 내용 |
| --- | --- |
| 주 Actor | 도로 관제사 |
| 목표 | 관제사가 등록된 장애물 이벤트의 전체 흐름과 처리 상태를 파악한다. |
| 사전 조건 | 하나 이상의 이벤트가 시스템에 등록되어 있다. |
| 기본 흐름 | 관제사는 이벤트 목록에서 장애물 종류, 발생 시각, 처리 상태, 우선순위 등 관제 판단에 필요한 요약 정보를 확인한다. |
| 대안 흐름 | 이벤트가 없는 경우 시스템은 표시할 이벤트가 없음을 알 수 있게 제공한다. |
| 사후 조건 | 관제사가 상세 확인할 이벤트를 선택할 수 있다. |

### UC-04. 이벤트 상세 확인

| 항목 | 내용 |
| --- | --- |
| 주 Actor | 도로 관제사 |
| 목표 | 관제사가 특정 이벤트의 실제 장애물 여부를 판단할 수 있는 정보를 확인한다. |
| 사전 조건 | 관제사가 목록 또는 알림에서 이벤트를 선택한다. |
| 기본 흐름 | 시스템은 선택된 이벤트의 위치, 장애물 종류, 신뢰도, 우선순위, 발생 시각, 처리 상태, 탐지 근거 정보를 제공한다. |
| 대안 흐름 | 일부 탐지 근거가 부족한 경우 관제사가 정보 부족 상태를 인지할 수 있어야 한다. |
| 사후 조건 | 관제사가 실제 장애물 여부와 후속 조치 필요성을 판단할 수 있다. |

### UC-05. 장애물 강조 영역 확인

| 항목 | 내용 |
| --- | --- |
| 주 Actor | 도로 관제사 |
| 목표 | 관제사가 탐지 근거 화면에서 AI가 장애물로 판단한 위치를 확인한다. |
| 사전 조건 | 이벤트에 장애물 강조 표시를 위한 좌표 정보가 포함되어 있다. |
| 기본 흐름 | 시스템은 프론트엔드가 장애물 강조 박스를 표시할 수 있는 정보를 제공하고, 관제사는 화면에서 강조 영역을 확인한다. |
| 대안 흐름 | 강조 표시 좌표가 없거나 표시가 불가능한 경우 관제사는 탐지 근거 부족 상태를 인지할 수 있어야 한다. |
| 사후 조건 | 관제사가 AI 탐지 결과의 위치적 타당성을 판단할 수 있다. |

### UC-06. 이벤트 상태 변경

| 항목 | 내용 |
| --- | --- |
| 주 Actor | 도로 관제사 |
| 목표 | 관제사가 이벤트의 처리 단계를 시스템에 반영한다. |
| 사전 조건 | 관제사가 이벤트 상세 정보를 확인한다. |
| 기본 흐름 | 관제사는 이벤트 상태를 미확인, 확인 중, 처리 완료, 오탐 등 업무 상태에 맞게 변경한다. 시스템은 변경된 상태를 저장한다. |
| 대안 흐름 | 이미 종료된 이벤트는 필요한 경우 정책에 따라 상태 변경을 제한할 수 있다. |
| 사후 조건 | 이벤트 목록과 상세 화면에서 최신 상태가 확인된다. |

### UC-07. 처리 기록 작성

| 항목 | 내용 |
| --- | --- |
| 주 Actor | 도로 관제사 |
| 목표 | 관제사가 확인 결과, 조치 내용, 오탐 사유 등을 기록한다. |
| 사전 조건 | 관제사가 이벤트를 확인하고 기록할 내용이 있다. |
| 기본 흐름 | 관제사는 이벤트에 대한 코멘트를 작성한다. 시스템은 코멘트를 이벤트와 관제사 정보에 연결해 저장한다. |
| 대안 흐름 | 코멘트 내용이 비어 있거나 너무 긴 경우 시스템은 저장하지 않아야 한다. |
| 사후 조건 | 이후 같은 이벤트를 조회할 때 처리 기록을 확인할 수 있다. |

### UC-08. 오탐 이벤트 구분

| 항목 | 내용 |
| --- | --- |
| 주 Actor | 도로 관제사 |
| 목표 | 실제 장애물이 아닌 AI 탐지 이벤트를 실제 처리 대상과 구분한다. |
| 사전 조건 | 관제사가 탐지 근거를 확인한 뒤 오탐이라고 판단한다. |
| 기본 흐름 | 관제사는 이벤트 상태를 오탐으로 변경하고, 필요한 경우 오탐 사유를 기록한다. |
| 대안 흐름 | 오탐 여부를 즉시 판단하기 어려운 경우 확인 중 상태로 유지한다. |
| 사후 조건 | 해당 이벤트는 미처리 장애물 목록과 구분되어 관리된다. |

## 6. Step 4 결론

이 시스템의 핵심 유스케이스는 **AI 탐지 이벤트 등록**과 **도로 관제사의 확인/판단/처리**로 나뉜다.

이후 기능 요구사항은 위 유스케이스를 기준으로 다음 항목을 빠짐없이 만족하도록 도출해야 한다.

1. AI 탐지 결과를 관제 이벤트로 등록할 수 있어야 한다.
2. 관제사는 신규 이벤트를 인지할 수 있어야 한다.
3. 관제사는 위치와 탐지 근거를 확인할 수 있어야 한다.
4. 관제사는 이벤트 상태를 변경할 수 있어야 한다.
5. 관제사는 처리 기록과 오탐 사유를 남길 수 있어야 한다.
