# Step 7. 데이터/권한/연계 요구사항 정의

## 1. 정의 기준

이 단계에서는 기능 요구사항과 비기능 요구사항을 바탕으로, 시스템이 다루어야 하는 데이터, 사용자 권한, 외부 파트 연계 요구사항을 정리한다.

구체적인 DB 컬럼 타입, API 경로, 인증 구현 방식은 아직 확정하지 않는다. 이 문서는 이후 `domain-modeling`, `database-design`, `implementation-prompt-writer` 단계의 입력으로 사용한다.

## 2. 데이터 요구사항

| ID | 데이터 요구사항 | 설명 | 관련 요구사항 |
| --- | --- | --- | --- |
| DR-01 | 시스템은 관제사를 식별할 수 있는 사용자 정보를 관리해야 한다. | 이벤트 처리자와 코멘트 작성자를 추적하기 위해 필요하다. | FR-11, FR-12 |
| DR-02 | 시스템은 탐지 장비를 식별할 수 있는 장비 정보를 관리해야 한다. | 어떤 장비가 이벤트를 탐지했는지 확인하기 위해 필요하다. | FR-01, FR-02 |
| DR-03 | 시스템은 AI가 탐지한 장애물 이벤트 정보를 관리해야 한다. | 관제 업무의 중심 데이터다. | FR-01~FR-10 |
| DR-04 | 이벤트에는 장애물 종류, 신뢰도, 위치, 발생 시각, 상태, 탐지 근거 정보가 포함되어야 한다. | 관제사가 실제 장애물 여부를 판단하는 기본 정보다. | FR-03, FR-08 |
| DR-05 | 이벤트에는 프론트엔드가 장애물 강조 박스를 표시할 수 있는 위치 정보가 포함되어야 한다. | bbox 정보는 관제사가 탐지 위치를 시각적으로 확인하는 데 필요하다. | FR-04, FR-19 |
| DR-06 | 이벤트에는 관제사가 확인 우선순위를 판단할 수 있는 우선순위 정보가 포함되어야 한다. | 다수 이벤트 발생 시 업무 순서를 정하는 데 필요하다. | FR-05 |
| DR-07 | 시스템은 이벤트별 처리 기록 또는 확인 메모를 관리해야 한다. | 처리 이력과 오탐 사유를 남기기 위해 필요하다. | FR-11, FR-12 |
| DR-08 | 시스템은 이벤트 상태를 관리해야 한다. | 미확인, 확인 중, 처리 완료, 오탐 등 업무 흐름을 구분하기 위해 필요하다. | FR-09, FR-10, FR-13 |
| DR-09 | 시스템은 정보가 부족한 탐지 결과를 정상 이벤트와 구분할 수 있어야 한다. | 관제 판단이 불가능한 데이터가 정상 처리되는 것을 방지한다. | FR-14 |

## 3. 권한 요구사항

| ID | 권한 요구사항 | 설명 | 미결정 여부 |
| --- | --- | --- | --- |
| AR-01 | 관제사만 관제 이벤트 목록과 상세 정보를 확인할 수 있어야 한다. | 관제 데이터 접근을 제한하기 위해 필요하다. | 인증 방식 미정 |
| AR-02 | 관제사만 이벤트 상태를 변경할 수 있어야 한다. | 임의 사용자의 상태 조작을 방지한다. | 인증 방식 미정 |
| AR-03 | 관제사만 이벤트 처리 기록 또는 코멘트를 작성할 수 있어야 한다. | 처리 이력의 신뢰성을 유지한다. | 인증 방식 미정 |
| AR-04 | AI 모듈 또는 허가된 장비만 신규 탐지 이벤트를 등록할 수 있어야 한다. | 무단 이벤트 생성을 방지한다. | AI 인증 방식 미정 |
| AR-05 | 관리자 역할이 필요한 경우 장비와 사용자 정보를 관리할 수 있어야 한다. | 장비/사용자 관리 범위는 추후 MVP 범위에서 결정한다. | 역할 범위 미정 |

## 4. AI 모듈 연계 요구사항

| ID | 연계 요구사항 | 설명 | 협의 필요 사항 |
| --- | --- | --- | --- |
| IR-AI-01 | AI 모듈은 장애물 탐지 결과를 백엔드에 전달할 수 있어야 한다. | 관제 이벤트 생성의 시작점이다. | 공식 요청 형식 |
| IR-AI-02 | AI 탐지 결과에는 관제 판단에 필요한 최소 정보가 포함되어야 한다. | 장애물 종류, 신뢰도, 위치, 탐지 근거 정보가 필요하다. | 필수/선택 필드 범위 |
| IR-AI-03 | AI 탐지 결과에는 장애물 강조 박스를 그릴 수 있는 bbox 정보가 포함되어야 한다. | 프론트엔드가 박스를 그릴 수 있도록 백엔드는 전달 가능한 형태로 유지해야 한다. | 좌표 기준, 기준점 |
| IR-AI-04 | AI 탐지 결과에는 탐지 근거 이미지 또는 영상 참조 정보가 포함되어야 한다. | 관제사가 실제 장애물 여부를 판단하기 위해 필요하다. | 이미지 파일 업로드 vs 참조 URL |
| IR-AI-05 | AI 모듈의 이벤트 등록 요청은 신뢰 가능한 요청인지 확인할 수 있어야 한다. | 무단 이벤트 등록 방지 목적이다. | API Key, 토큰, IP 제한 등 |

다음 사항은 **AI 파트와 협의해서 결정해 주세요.**

- AI -> 백엔드 공식 데이터 전달 형식
- 이미지 파일 직접 업로드 여부 또는 이미지/영상 URL 전달 여부
- bbox 좌표가 픽셀 기준인지 정규화 좌표 기준인지
- `bbox_x`, `bbox_y`가 좌상단 기준인지 중심점 기준인지
- AI 이벤트 등록 요청 인증 방식

## 5. 프론트엔드 연계 요구사항

| ID | 연계 요구사항 | 설명 | 협의 필요 사항 |
| --- | --- | --- | --- |
| IR-FE-01 | 프론트엔드는 신규 이벤트를 관제사가 인지할 수 있게 표시해야 한다. | 관제사의 빠른 인지를 지원한다. | 알림 방식 |
| IR-FE-02 | 프론트엔드는 이벤트 목록을 표시할 수 있어야 한다. | 관제사가 전체 이벤트 상태를 확인한다. | 목록 표시 필드 |
| IR-FE-03 | 프론트엔드는 이벤트 상세 정보를 표시할 수 있어야 한다. | 관제사가 위치, 신뢰도, 상태, 탐지 근거를 확인한다. | 상세 표시 필드 |
| IR-FE-04 | 프론트엔드는 bbox 정보를 사용해 장애물 강조 박스를 표시할 수 있어야 한다. | 관제사가 AI 탐지 위치를 시각적으로 확인한다. | bbox 매핑 방식 |
| IR-FE-05 | 프론트엔드는 관제사의 상태 변경 결과를 시스템에 반영할 수 있어야 한다. | 처리 흐름 관리에 필요하다. | 상태값 표현 방식 |
| IR-FE-06 | 프론트엔드는 관제사의 처리 기록 작성과 조회를 지원해야 한다. | 조치 이력 확인에 필요하다. | 코멘트 UI/표시 방식 |

다음 사항은 **프론트엔드 파트와 협의해서 결정해 주세요.**

- 신규 이벤트 알림 방식
- 이벤트 목록에 반드시 표시할 요약 정보
- 이벤트 상세 화면에 표시할 정보
- bbox 좌표를 실제 이미지/영상 화면에 매핑하는 방식
- 상태값과 우선순위를 화면에서 어떻게 표현할지
- 실시간 영상 소스를 프론트엔드가 직접 연결할지, 백엔드가 참조 정보를 제공할지

## 6. 백엔드 책임 요구사항

| ID | 백엔드 책임 | 설명 |
| --- | --- | --- |
| BR-01 | AI 탐지 결과를 수신한다. | 공식 형식은 추후 확정하되 수신 책임은 백엔드에 있다. |
| BR-02 | 탐지 결과를 관제 이벤트로 저장한다. | 관제사가 조회하고 처리할 수 있어야 한다. |
| BR-03 | 프론트엔드가 목록과 상세 화면을 구성할 수 있도록 이벤트 정보를 제공한다. | 프론트엔드 표시를 위한 안정적인 데이터 공급이 필요하다. |
| BR-04 | 이벤트 상태 변경을 반영한다. | 관제 업무 흐름을 저장해야 한다. |
| BR-05 | 이벤트별 처리 기록을 저장하고 조회 가능하게 한다. | 조치 이력을 유지해야 한다. |
| BR-06 | 권한 없는 요청이나 필수 정보가 부족한 요청을 정상 이벤트와 구분한다. | 데이터 품질과 보안을 유지해야 한다. |

## 8. Step 7 결론

데이터/권한/연계 요구사항의 핵심은 다음과 같다.

1. 시스템은 관제사, 장비, 이벤트, 처리 기록을 구분해서 관리해야 한다.
2. 이벤트는 관제 판단에 필요한 위치, 신뢰도, 상태, 우선순위, 탐지 근거, bbox 정보를 포함해야 한다.
3. 관제사 기능과 AI 이벤트 등록에는 접근 통제가 필요하다.
4. AI와 프론트엔드의 세부 데이터 연계 방식은 아직 미정이며, 반드시 각 파트와 협의해서 결정해야 한다.
5. 백엔드는 AI 탐지 결과와 프론트 관제 화면 사이의 안정적인 데이터 중계 책임을 가진다.
