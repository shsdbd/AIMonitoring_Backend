# Step 5. 릴리스 마일스톤 설계

## 1. 마일스톤 설계 기준

릴리스 계획은 1주일 단위로 구성한다.

이 계획은 구현 상세가 아니라 MVP 범위 달성을 위한 작업 순서와 검증 목표를 정의한다. 실제 티켓 분해는 이후 `task-breakdown` 단계에서 수행한다.

## 2. 1주차: 모델 정합성 및 이벤트 기본 흐름 복구

| 항목 | 내용 |
| --- | --- |
| 목표 | 현재 Event 중심 프로토타입의 모델/스키마/API 불일치를 정리하고, 이벤트 생성-조회-상태 변경 흐름을 정상화한다. |
| 주요 범위 | Event 기본 정보, 위치 정보, bbox, priority, 상태값, 탐지 근거 정보 정합성 확보 |
| 완료 기준 | 신규 이벤트 등록, 목록 조회, 상태 변경, 최신 상태 재조회가 정상 동작한다. |
| 주의사항 | User/Equipment/Comment 전체 확장보다 MVP 이벤트 흐름 복구를 우선한다. |

## 3. 2주차: 관제사 확인 흐름 강화

| 항목 | 내용 |
| --- | --- |
| 목표 | 관제사가 목록과 상세 화면에서 판단에 필요한 정보를 확인할 수 있도록 백엔드 제공 데이터를 정리한다. |
| 주요 범위 | 목록/상세 응답에 필요한 이벤트 요약/상세 정보, 오탐 구분, 탐지 근거 참조, bbox 정보 제공 |
| 완료 기준 | 프론트엔드가 신규/미처리 이벤트, 상세 정보, 장애물 강조 박스 데이터를 사용할 수 있다. |
| 주의사항 | 프론트엔드 표시 필드는 프론트 파트와 협의가 필요하다. |

## 4. 3주차: AI/프론트 연계 계약 확정 및 통합 검증

| 항목 | 내용 |
| --- | --- |
| 목표 | AI -> 백엔드 -> 프론트엔드로 이어지는 데이터 전달 계약을 맞추고 통합 흐름을 검증한다. |
| 주요 범위 | AI 요청 형식, bbox 기준, priority 체계, 이미지/영상 참조 방식, 신규 이벤트 인지 방식 협의 |
| 완료 기준 | AI 또는 테스트 클라이언트가 만든 탐지 이벤트가 프론트 관제 화면에서 확인 가능하다. |
| 주의사항 | AI 파트가 준비되지 않은 경우 테스트 요청 데이터로 통합 흐름을 먼저 검증한다. |

## 5. 4주차: MVP 시연 안정화 및 문서 정리

| 항목 | 내용 |
| --- | --- |
| 목표 | 졸업 작품 시연에 필요한 핵심 흐름을 안정화하고 문서를 정리한다. |
| 주요 범위 | 시연 데이터 준비, 오류 케이스 확인, Swagger/README/결정 문서 정리 |
| 완료 기준 | 시연 흐름을 반복 실행해도 이벤트 등록, 확인, 상태 변경이 일관되게 동작한다. |
| 주의사항 | Should-have 기능 추가보다 Must-have 안정화를 우선한다. |

## 6. 마일스톤별 범위 통제

| 시점 | 범위 통제 원칙 |
| --- | --- |
| 1주차 종료 | 이벤트 기본 흐름이 불안정하면 Should-have 기능으로 넘어가지 않는다. |
| 2주차 종료 | 프론트가 필요한 표시 데이터가 불명확하면 프론트 파트와 즉시 협의한다. |
| 3주차 종료 | AI 파트가 미완성이라도 백엔드 테스트 입력으로 통합 흐름을 고정한다. |
| 4주차 | 새 기능 추가보다 시연 안정성과 문서 정합성을 우선한다. |

## 7. Step 5 결론

MVP 릴리스는 4주 단위로 다음 순서를 따른다.

1. 이벤트 기본 흐름 복구
2. 관제사 확인 흐름 강화
3. AI/프론트 연계 계약 확정
4. 시연 안정화 및 문서 정리

마일스톤 전체에서 Must-have 안정화를 최우선으로 하고, Should-have는 일정이 남을 때만 포함한다.
