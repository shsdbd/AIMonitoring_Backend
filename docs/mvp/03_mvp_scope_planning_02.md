# Step 2. 핵심 가치 사슬(Value Chain) 정의

## 1. 가치 사슬 정의 목적

핵심 가치 사슬은 장애물 탐지부터 관제사의 처리 판단까지 이어지는 최소 필수 흐름이다.

이 흐름에 포함되지 않는 기능은 MVP의 핵심 가치를 직접 증명하지 못하므로 Should-have, Could-have 또는 Won't-have로 분리한다.

## 2. MVP Critical Path

```text
1. AI가 도로 위 동물 사체를 탐지한다.
2. AI가 탐지 결과를 백엔드에 전달한다.
3. 백엔드가 탐지 결과를 장애물 이벤트로 등록한다.
4. 프론트엔드가 신규 이벤트를 관제사에게 보여준다.
5. 관제사가 이벤트 목록에서 신규/미처리 이벤트를 확인한다.
6. 관제사가 이벤트 상세에서 위치, 신뢰도, 탐지 근거, bbox 강조 정보, 우선순위를 확인한다.
7. 관제사가 실제 장애물 여부를 판단한다.
8. 관제사가 이벤트 상태를 확인 중, 처리 완료, 오탐 중 하나로 변경한다.
9. 백엔드가 변경된 상태를 저장한다.
10. 프론트엔드가 최신 상태를 다시 보여준다.
```

## 3. 가치 사슬 단계별 필요 기능

| 단계 | 가치 사슬 | 필요한 기능 | MVP 필요성 |
| --- | --- | --- | --- |
| 1 | AI 탐지 | AI 모델이 장애물을 탐지 | 백엔드 범위 밖, 시뮬레이션/AI 파트 결과로 대체 |
| 2 | 탐지 결과 전달 | 백엔드가 탐지 결과를 받을 수 있음 | 필수 |
| 3 | 이벤트 등록 | 탐지 결과를 관제 이벤트로 저장 | 필수 |
| 4 | 신규 이벤트 표시 | 프론트가 신규 이벤트를 확인 가능 | 필수 |
| 5 | 목록 확인 | 관제사가 이벤트 목록 확인 | 필수 |
| 6 | 상세 확인 | 위치, 신뢰도, 이미지/영상 참조, bbox, priority 확인 | 필수 |
| 7 | 관제 판단 | 관제사가 실제 장애물/오탐 여부 판단 | 필수 |
| 8 | 상태 변경 | 관제사가 상태 변경 | 필수 |
| 9 | 상태 저장 | 변경 결과 저장 | 필수 |
| 10 | 최신 상태 재조회 | 프론트가 변경 결과 확인 | 필수 |

## 4. MVP에서 유지할 상태 흐름

| 상태 | 의미 | MVP 포함 여부 |
| --- | --- | --- |
| `UNCHECKED` | AI가 등록했지만 관제사가 아직 확인하지 않은 이벤트 | 포함 |
| `CHECKING` | 관제사가 확인 중인 이벤트 | 포함 |
| `COMPLETED` | 실제 장애물로 판단되어 처리 완료된 이벤트 | 포함 |
| `MISIDENTIFIED` | 오탐으로 판단된 이벤트 | 포함 |

## 5. 가치 사슬에 직접 포함되지 않는 기능

| 기능 | 판단 |
| --- | --- |
| 관제사 로그인/권한 세분화 | 실제 서비스에는 필요하지만 MVP 핵심 흐름 검증에는 우회 가능 |
| 코멘트/처리 기록 | 업무 완성도는 높지만 상태 변경만으로 최소 처리 흐름 검증 가능 |
| 사용자/장비 관리 화면 | 관제 흐름의 선행 관리 기능이며 MVP 핵심 시연에는 불필요 |
| 통계 대시보드 | 관제 흐름 이후의 분석 기능이므로 제외 |
| 다중 객체 탐지 | 현재 범위는 이벤트당 단일 장애물 기준 |
| 상태 변경 이력 테이블 | MVP에서는 최신 상태만으로 시연 가능 |

## 6. Step 2 결론

MVP Critical Path는 **탐지 결과 수신 -> 이벤트 등록 -> 관제사 확인 -> 상태 변경 -> 최신 상태 확인**이다.

이 흐름에 직접 필요한 데이터는 다음으로 제한한다.

- 장애물 종류
- 신뢰도
- 위치 정보
- 탐지 근거 이미지 또는 영상 참조
- bbox 강조 정보
- priority
- 이벤트 상태
- 발생 시각
