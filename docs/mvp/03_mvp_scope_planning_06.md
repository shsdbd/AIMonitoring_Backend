# Step 6. 최종 MVP 범위 정의서

## 1. 문서 목적

이 문서는 `mvp-scope-planning` 단계의 최종 산출물이다.

목적은 요구사항 분해 단계에서 도출된 기능 중 졸업 작품 MVP에서 반드시 구현할 범위와 이번 차수에서 제외할 범위를 명확히 확정하는 것이다.

## 2. MVP 핵심 목표

MVP의 목표는 다음 문장으로 정의한다.

> AI가 탐지한 도로 위 동물 사체 이벤트가 백엔드를 통해 관제사 화면에 전달되고, 관제사가 위치와 탐지 근거를 확인한 뒤 이벤트 상태를 관리할 수 있다.

## 3. MVP Critical Path

```text
AI 탐지 결과 발생
-> 백엔드 이벤트 등록
-> 프론트엔드 신규 이벤트 표시
-> 관제사 목록/상세 확인
-> 위치, 신뢰도, 탐지 근거, bbox 강조 정보, priority 확인
-> 관제사 실제 장애물 여부 판단
-> 상태 변경
-> 최신 상태 저장 및 재조회
```

## 4. MVP 포함 범위

| ID | 포함 기능 | 설명 |
| --- | --- | --- |
| IN-01 | AI 탐지 결과 수신 | AI 또는 테스트 클라이언트가 전달한 탐지 결과를 백엔드가 받을 수 있어야 한다. |
| IN-02 | 신규 이벤트 등록 | 탐지 결과를 관제 이벤트로 저장한다. |
| IN-03 | 이벤트 목록 제공 | 관제사가 신규/미처리 이벤트를 확인할 수 있어야 한다. |
| IN-04 | 이벤트 상세 제공 | 관제사가 선택한 이벤트의 판단 정보를 확인할 수 있어야 한다. |
| IN-05 | 위치 정보 제공 | 장애물 발생 위치를 확인할 수 있어야 한다. |
| IN-06 | 탐지 근거 제공 | 이미지 또는 영상 참조 정보를 통해 관제사가 탐지 근거를 확인할 수 있어야 한다. |
| IN-07 | bbox 정보 제공 | 프론트엔드가 장애물 강조 박스를 그릴 수 있는 정보를 제공한다. |
| IN-08 | priority 제공 | 관제사가 이벤트 확인 우선순위를 판단할 수 있도록 한다. |
| IN-09 | 이벤트 상태 변경 | 관제사가 확인 중, 처리 완료, 오탐 등으로 상태를 변경할 수 있어야 한다. |
| IN-10 | 오탐 구분 | 실제 장애물이 아닌 이벤트를 실제 처리 대상과 구분한다. |
| IN-11 | 최신 상태 재조회 | 상태 변경 후 목록/상세에서 최신 상태를 확인할 수 있어야 한다. |
| IN-12 | 필수 정보 검증 | 관제 판단에 필요한 필수 정보가 부족한 데이터를 정상 이벤트와 구분한다. |

## 5. MVP 조건부 포함 범위

| ID | 조건부 포함 기능 | 포함 조건 |
| --- | --- | --- |
| CI-01 | 처리 기록/코멘트 작성 | Must-have 구현이 안정화되고 일정이 남는 경우 포함한다. |
| CI-02 | 처리 기록/코멘트 조회 | CI-01을 포함하는 경우 함께 포함한다. |
| CI-03 | 관제사 식별 정보 관리 | 단일 관제사 가정을 넘어서 처리자 기록이 필요해질 경우 포함한다. |
| CI-04 | 장비 식별 정보 관리 | 장비 도메인 구현이 MVP 일정에 부담을 주지 않는 경우 포함한다. |
| CI-05 | 단순 접근 통제 | 시연 또는 보안 요구상 반드시 필요하다고 판단되면 최소 수준으로 포함한다. |
| CI-06 | AI 요청 신뢰성 확인 | AI 파트와 요청 형식이 확정된 뒤 최소 수준으로 포함한다. |

## 6. MVP 제외 범위

| ID | 제외 기능 | 제외 사유 |
| --- | --- | --- |
| OOS-01 | AI 모델 학습 및 추론 로직 | AI 파트 책임이다. |
| OOS-02 | 프론트엔드 화면 디자인 세부 구현 | 프론트엔드 파트 책임이다. |
| OOS-03 | 고도화된 통계/분석 대시보드 | 관제 흐름 이후의 분석 기능이다. |
| OOS-04 | 대규모 분산 처리 인프라 | MVP에 과도하다. |
| OOS-05 | 완전한 고가용성 구성 | 단일 백엔드/DB 시연을 우선한다. |
| OOS-06 | 다중 객체 탐지를 위한 별도 Detection 도메인 | 현재는 이벤트당 단일 장애물 탐지로 제한한다. |
| OOS-07 | 별도 EventStatusHistory 이력 테이블 | MVP에서는 최신 상태와 조건부 코멘트로 충분하다. |
| OOS-08 | Equipment 자체 지도 좌표 관리 | Event 위치 정보로 지도 표시가 가능하다. |
| OOS-09 | 복잡한 역할/권한 관리 | MVP 핵심 흐름에 직접 필요하지 않다. |
| OOS-10 | 관리자용 사용자/장비 관리 고도화 | 운영 관리 기능이며 핵심 시연 범위가 아니다. |

## 7. MVP 완료 기준

| 기준 | 설명 |
| --- | --- |
| 이벤트 등록 | AI 또는 테스트 클라이언트가 보낸 탐지 결과가 이벤트로 등록된다. |
| 목록 확인 | 관제사가 등록된 이벤트 목록을 확인할 수 있다. |
| 상세 확인 | 관제사가 위치, 신뢰도, 탐지 근거, bbox, priority를 확인할 수 있다. |
| 상태 변경 | 관제사가 이벤트 상태를 확인 중, 처리 완료, 오탐 중 하나로 변경할 수 있다. |
| 재조회 | 상태 변경 결과가 저장되고 다시 조회된다. |
| 오탐 처리 | 오탐 이벤트가 실제 처리 대상과 구분된다. |

## 8. 릴리스 마일스톤

| 주차 | 목표 | 완료 기준 |
| --- | --- | --- |
| 1주차 | 모델 정합성 및 이벤트 기본 흐름 복구 | 이벤트 생성, 조회, 상태 변경 흐름 정상화 |
| 2주차 | 관제사 확인 흐름 강화 | 프론트가 목록/상세/bbox/priority 데이터를 사용할 수 있음 |
| 3주차 | AI/프론트 연계 계약 확정 및 통합 검증 | 탐지 이벤트가 관제 화면에서 확인 가능 |
| 4주차 | MVP 시연 안정화 및 문서 정리 | 시연 흐름 반복 실행 가능 |

## 9. 협의 필요 사항

다음 항목은 MVP에 영향을 주지만 현재 확정하지 않는다. 각 파트와 협의 후 후속 문서에서 결정한다.

| 항목 | 협의 대상 |
| --- | --- |
| AI -> 백엔드 공식 요청 형식 | AI 파트 |
| 이미지 파일 업로드 또는 이미지/영상 URL 전달 여부 | AI 파트, 프론트엔드 파트 |
| bbox 좌표 기준과 기준점 | AI 파트, 프론트엔드 파트 |
| 프론트엔드 신규 이벤트 알림 방식 | 프론트엔드 파트 |
| priority 값 체계 | 전체 팀 |
| 처리 기록 기능의 MVP 포함 여부 | PO 결정 |

## 10. 최종 결론

이번 MVP는 기능을 넓히는 것이 아니라 **AI 탐지 이벤트가 관제사의 판단과 상태 처리로 이어지는 최소 관제 흐름**을 안정적으로 완성하는 데 집중한다.

이후 단계에서는 본 문서의 포함 범위와 제외 범위를 기준으로 도메인 모델링, 데이터베이스 설계, 작업 분해, 구현 지시서를 작성한다.
