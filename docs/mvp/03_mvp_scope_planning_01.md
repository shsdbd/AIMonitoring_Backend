# Step 1. 전체 요구사항 및 목표 검토

## 1. 검토 목적

이 단계는 `requirements-decomposition`에서 도출된 요구사항을 모두 구현 대상으로 보지 않고, 졸업 작품 MVP에서 반드시 증명해야 하는 핵심 가치만 다시 압축하기 위한 검토 단계다.

## 2. 상위 목표 요약

| 항목 | 내용 |
| --- | --- |
| 프로젝트명 | AI 기반 실시간 도로 장애물 관제 시스템 |
| 핵심 탐지 대상 | 도로 위 동물 사체 |
| 1차 사용자 | 도로 관제사 |
| 핵심 문제 | 사람이 직접 순찰하거나 CCTV 영상을 감시해야 해서 장애물 발견이 늦어진다. |
| 백엔드 핵심 가치 | AI 모델과 프론트엔드 사이의 안정적인 데이터 전달, 빠른 데이터 처리 |
| 최종 시연 장면 | AI 탐지 이벤트가 백엔드를 거쳐 프론트 관제 화면에 표시되고, 관제사가 위치/탐지 근거/강조 박스를 확인한 뒤 상태를 변경한다. |

## 3. 요구사항 단계 핵심 결론

| 구분 | 결론 |
| --- | --- |
| 핵심 시나리오 | AI 탐지 -> 이벤트 등록 -> 관제사 인지 -> 상세 확인 -> 상태 변경 |
| 핵심 유스케이스 | AI 탐지 이벤트 등록, 신규 이벤트 인지, 목록/상세 확인, 장애물 강조 영역 확인, 상태 변경, 오탐 구분 |
| Must-have | 탐지 결과 수신, 이벤트 등록, 목록/상세 확인, 위치/탐지 근거/bbox/priority 제공, 상태 변경, 오탐 구분 |
| Should-have | 처리 기록, 관제사/장비 식별 정보 관리, 권한 통제, AI 요청 신뢰성 확인 |
| Won't-have | AI 모델 구현, 프론트 디자인 세부 구현, 대규모 인프라, 다중 객체 Detection, 별도 상태 이력 테이블 |

## 4. MVP 관점의 핵심 가치

MVP에서 증명해야 할 가치는 “모든 관제 시스템 기능을 갖춘다”가 아니다.

MVP의 핵심 가치는 다음 하나로 압축한다.

> AI가 감지한 도로 장애물 이벤트가 백엔드를 통해 관제사에게 전달되고, 관제사가 이를 확인한 뒤 처리 상태를 관리할 수 있다.

## 5. MVP 성공을 위해 반드시 남겨야 할 흐름

```text
AI 탐지 결과 발생
-> 백엔드 이벤트 등록
-> 프론트엔드 이벤트 표시
-> 관제사 목록/상세 확인
-> 위치, 탐지 근거, bbox 강조 정보 확인
-> 관제사 상태 변경
-> 최신 상태 재조회
```

## 6. 범위 통제 원칙

| 원칙 | 설명 |
| --- | --- |
| 관제 흐름 우선 | 관제사가 이벤트를 확인하고 상태를 바꾸는 흐름에 직접 기여하지 않으면 후순위로 둔다. |
| 연동 안정성 우선 | AI와 프론트 사이의 데이터 전달에 필요한 기능을 우선한다. |
| 시연 가능성 우선 | 졸업 작품에서 눈으로 확인 가능한 동작 흐름을 먼저 완성한다. |
| 운영 고도화 후순위 | 인증, 관리자 기능, 통계, 대규모 인프라는 MVP 이후로 미룬다. |
| 과설계 금지 | 다중 객체 탐지, 별도 이력 테이블 등은 현재 문제 범위를 넘어서므로 제외한다. |

## 7. Step 1 결론

MVP는 “AI 기반 관제 플랫폼 전체”가 아니라, **AI 탐지 이벤트가 도로 관제사의 확인과 상태 처리로 이어지는 최소 작동 흐름**을 완성하는 데 집중한다.

따라서 다음 단계에서는 이 최소 흐름을 핵심 가치 사슬로 정의하고, 그 흐름에 직접 기여하지 않는 기능은 제외 또는 후순위로 분리한다.
